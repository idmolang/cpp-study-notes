# p1-1 | 코드가 프로그램이 되기까지 | Ch 0.5
sum: 내가 쓴 `.cpp` 파일은 바로 실행되지 않아요. **전처리 → 컴파일 → 링크** 세 단계를 거쳐야 실행 파일이 돼요.
ana: 🍳 여러 사람이 요리를 나눠 만드는 것과 같아요. 재료를 손질하고(전처리), 각자 자기 요리를 하고(컴파일), 마지막에 한 상에 모아 차려요(링크).
h: 세 단계가 각각 하는 일
p: C++ 코드는 사람이 읽는 글이라서 컴퓨터가 바로 실행할 수 없어요. 그래서 `g++` 같은 프로그램이 세 단계에 걸쳐 실행 파일로 바꿔 줘요.
flow: ① 전처리 > `#include <iostream>` 같은 줄을 만나면 그 파일 내용을 그 자리에 통째로 복사해 붙여요 || ② 컴파일 > `.cpp` 파일을 **하나씩 따로** 기계어로 번역해요. 결과물은 `.o` 파일 || ③ 링크 > 번역된 `.o` 조각들을 이어 붙여 실행 파일 하나로 만들어요
h: 왜 단계를 알아야 하나요? — 오류를 읽기 위해서
p: 오류가 났을 때 “어느 단계에서 난 오류인지”를 알면 어디를 고쳐야 할지 바로 보여요. 두 오류는 생김새가 확실히 달라요.
tbl:  | 컴파일 오류 | 링크 오류
r: 언제 나나요 | 파일 하나를 번역하다가 | 조각을 이어 붙이다가
r: 주로 원인 | 문법이 틀렸거나, 모르는 이름을 썼을 때 | 함수를 선언만 하고 몸통(정의)을 안 만들었을 때
r: 메시지 모양 | `main.cpp:5:12: error: expected ';'` 처럼 **줄 번호**가 있어요 | 줄 번호 없이 `undefined reference to 'add'`
h: 컴파일러는 파일을 하나씩만 본다
p: 컴파일러는 `main.cpp`를 번역하는 동안 `add.cpp`가 있는지조차 몰라요. 그래서 다른 파일에 있는 함수를 쓰려면 “이런 함수가 어딘가 있어요”라고 미리 알려 줘야 해요(1-7 전방 선언에서 자세히).
code:
g++ -c main.cpp          # 번역만 → main.o 가 생김
g++ -c add.cpp           # 번역만 → add.o 가 생김
g++ main.o add.o -o app  # 이어 붙이기(링크) → 실행 파일 app
:end
p: 위 세 줄은 단계를 눈으로 보려고 나눈 것이에요. 보통은 `g++ main.cpp add.cpp -o app` 한 줄로 세 단계를 한 번에 해요. `-c`는 “번역(compile)까지만 하고 멈춰”라는 뜻이에요.
star: 오류 메시지에 **줄 번호**가 있으면 컴파일 오류, 줄 번호 없이 **`undefined reference`** 가 나오면 링크 오류예요.
trap: `g++ main.cpp -o app` 으로만 빌드 (add.cpp 를 빠뜨림) > `g++ main.cpp add.cpp -o app` > main.cpp 는 번역되지만 add 의 몸통을 못 찾아서 링크 오류가 나요
mem: `-c` = **c**ompile only. “이어 붙이기 직전에서 멈춰.”
key: 빌드 순서는 전처리 → 컴파일 → 링크
key: 줄 번호가 있으면 컴파일 오류, `undefined reference` 면 링크 오류
key: 컴파일러는 .cpp 파일을 하나씩 따로 번역해요

# p1-2 | Debug 와 Release, 그리고 첫 프로그램 | Ch 0.7~0.9
sum: 개발할 때는 **Debug**(느리지만 한 줄씩 따라가기 쉬움), 완성해서 내보낼 때는 **Release**(빠름)로 빌드해요. main 이 돌려주는 0은 “성공”이라는 뜻이에요.
ana: 🚗 Debug는 교습용 자동차예요. 천천히 가지만 강사가 옆에서 매 순간을 볼 수 있어요. Release는 경주용 자동차라서 빠르지만 안을 들여다보기 어려워요.
h: 두 빌드 방식의 차이
p: 같은 코드라도 어떤 옵션으로 빌드하느냐에 따라 결과물이 달라져요. Release는 컴파일러가 코드를 빠르게 만들려고 순서를 바꾸거나 합치기 때문에, 디버거로 한 줄씩 따라가기가 어려워요.
tbl:  | Debug | Release
r: 최적화 | 끔 | 켬
r: 실행 속도 | 느림 | 빠름
r: 디버거로 한 줄씩 보기 | 쉬움 | 어려움 (흐름이 뒤섞임)
r: 언제 쓰나요 | 개발하고 버그 잡을 때 | 배포할 때, 속도를 잴 때
warn: Debug에서는 잘 되는데 Release에서만 이상하게 깨진다면, 컴파일러 문제가 아니라 거의 항상 **내 코드 속 미정의 동작(UB)** 때문이에요. 예를 들어 초기화하지 않은 변수를 읽는 코드가 있으면 Debug에서는 우연히 0이 나오다가 Release에서 엉뚱한 값이 나와요.
h: 첫 프로그램 한 줄씩 보기
code:
#include <iostream>

int main()
{
    std::cout << "Hello, world!\n";
    return 0;
}
:end
out: 실행 결과
Hello, world!
:end
tbl: 줄 | 뜻
r: `#include <iostream>` | 화면 출력 기능(`std::cout`)이 들어 있는 파일을 가져와요
r: `int main()` | 프로그램이 시작하는 곳이에요. 반드시 하나만 있어야 해요
r: `std::cout << "..."` | 따옴표 안의 글자를 화면에 출력해요. `\n` 은 줄바꿈이에요
r: `return 0;` | “성공적으로 끝났어요”라고 운영체제에 알려 줘요 (0 = 성공)
h: 자주 보는 오류 두 가지
tbl: 오류 메시지 | 원인과 해결
r: `iostream: No such file` | 표준 헤더는 `< >` 로, 내가 만든 파일은 `" "` 로 감싸야 해요
r: `undefined reference to main` | main 함수가 없거나 철자를 틀렸어요 (Main, mian)
star: main의 반환값은 **종료 코드**예요. **0이면 성공**, 0이 아니면 실패를 뜻해요.
trap: Debug 빌드로 프로그램 속도를 잼 > Release 빌드로 잰다 > Debug는 일부러 최적화를 꺼서 실제 속도와 달라요
mem: **D**ebug = **D**etective(탐정처럼 천천히 조사), **R**elease = **R**ace(경주)
key: 개발할 땐 Debug, 배포·속도 측정은 Release
key: Release에서만 깨지면 미정의 동작을 의심해요
key: `return 0;` 은 “성공”이라는 뜻

# p1-3 | 프로그램의 뼈대와 변수 | Ch 1.1~1.3
sum: C++ 프로그램은 **문장**이 모여 **함수**가 되고, 실행은 언제나 **main 함수**에서 시작해요. **변수**는 값을 담는 이름 붙은 메모리 칸이에요.
ana: 📦 변수는 이름표를 붙인 상자예요. 상자 자체(메모리 칸)를 “객체”라고 부르고, 거기에 붙인 이름표가 변수 이름이에요.
h: 프로그램을 이루는 네 가지
p: 아래 코드 한 개 안에 네 가지가 모두 들어 있어요. 주석을 따라가며 보세요.
code:
#include <iostream>          // ① 전처리기 지시문 — # 으로 시작, 세미콜론 없음

int main()                   // ② 함수 — 여기서는 프로그램 시작점인 main
{
    int x { 5 };             // ③ 문장 — 변수 x 를 만들고 5 를 넣음
    std::cout << x << '\n';  // ③ 문장 — x 를 출력
    return 0;                // ③ 문장 — 성공으로 끝냄
}                            // ④ 주석은 // 뒤에 쓰고, 컴파일러는 무시해요
:end
out: 실행 결과
5
:end
tbl: 이름 | 뜻
r: 문장 (statement) | 컴퓨터에게 시키는 일 하나. 대부분 `;` 으로 끝나요
r: 함수 (function) | 문장 여러 개를 묶어 이름을 붙인 것
r: main | 프로그램 시작점. 프로그램에 **딱 하나**, 반환형은 **int**
r: 전처리기 지시문 | `#` 으로 시작하고 컴파일 전에 처리돼요. 끝에 `;` 이 없어요
h: 객체와 변수
p: C++에서 “객체”는 값을 담으려고 잡아 둔 메모리 칸을 말해요. 클래스와는 상관없는 말이라서 `int x;` 의 x도 객체예요. 그 객체에 이름을 붙인 것이 변수예요.
code:
int width { 10 };     // 한 줄에 변수 하나씩 — 권장
int height { 20 };
int a, b;             // 같은 타입 두 개를 한 줄에 — 되긴 하지만 비권장
// int c, double d;   // ❌ 타입이 다른 변수는 한 문장에 못 씀
:end
h: 변수를 만드는 좋은 습관
li: 변수는 **처음 쓰기 직전에** 만들어요. 그때 넣을 값이 생기니까요
li: **한 줄에 하나씩** 만들어요. 읽기 쉽고 실수가 줄어요
li: 주석에는 “무엇을 하는지”보다 **“왜 이렇게 했는지”** 를 써요. `// x를 1 증가` 보다 `// 인덱스가 0부터라서 1을 더함` 이 쓸모 있어요
star: C++의 “객체”는 클래스와 상관없는 말이에요. **`int x;` 도 객체**예요.
trap: `int a, double b;` > 줄을 나눠서 `int a {};` `double b {};` > 한 문장에는 같은 타입의 변수만 만들 수 있어요
trap: `int main` 대신 `void main` > `int main()` > 표준 C++에서 main의 반환형은 int로 정해져 있어요
mem: 상자(객체) + 이름표(변수 이름) = 변수
key: 실행은 main에서 시작 (하나뿐, 반환형 int)
key: 객체 = 메모리 칸, 변수 = 이름 붙은 객체
key: 변수는 쓰기 직전에, 한 줄에 하나씩

# p1-4 | 초기화: 만들자마자 값 넣기 | Ch 1.4, 1.6
sum: 변수는 만들자마자 **중괄호 `{ }` 로 값을 넣어요**. 값을 안 넣은 변수를 읽으면 무슨 일이 생길지 모르는 **미정의 동작(UB)** 이 돼요.
ana: 🏠 새 집에 이사 왔는데 청소를 안 하면 전 주인이 두고 간 물건이 그대로 있어요. 변수도 값을 안 넣으면 그 메모리에 남아 있던 아무 값이나 들어 있어요. `{ }` 는 입주 청소예요.
h: 값을 넣는 다섯 가지 방법 — 하나만 기억하면 돼요
p: C++에는 변수에 처음 값을 넣는 방법이 여러 개 있어요. 이 과정에서는 **중괄호 방식**을 기본으로 써요.
tbl: 코드 | 결과 | 쓸까요?
r: `int a;` | 값이 뭔지 모름 | ❌ 위험
r: `int b = 5;` | 5 | 되긴 하지만 실수를 못 잡아요
r: `int c ( 5 );` | 5 | 되긴 하지만 함수 선언과 헷갈려요
r: `int d { 5 };` | 5 | ✅ **이걸 써요**
r: `int e {};` | 0 | ✅ 아직 넣을 값이 없을 때
h: 왜 하필 중괄호일까요?
p: 중괄호는 “값이 잘려 나가는 실수”를 컴파일할 때 잡아 줘요. 4.9를 int에 넣으면 소수점이 사라져 4가 되는데, `=` 는 이걸 조용히 넘기고 `{ }` 는 오류로 막아요.
vs: = 로 넣으면 | { } 로 넣으면
int n = 4.9;
std::cout << n;
// 출력: 4
// 0.9 가 조용히 사라짐
--
int n { 4.9 };
// 컴파일 오류!
// narrowing conversion
// → 실수를 바로 알려 줌
:end
term: 축소 변환 | narrowing conversion | 큰 값을 작은 타입에 넣으면서 값이 잘려 나가는 변환 (4.9 → 4)
h: 값을 안 넣으면 생기는 일 — 미정의 동작
code:
#include <iostream>

int main()
{
    int x;                   // 값을 안 넣음
    std::cout << x << '\n';  // ❌ 무엇이 출력될지 모름
    return 0;
}
:end
p: 이 코드는 실행할 때마다 다른 값이 나올 수도 있고, 운 좋게 항상 0이 나올 수도 있어요. **항상 0이 나오는 경우가 더 위험해요.** 버그가 숨어 있다가 다른 컴퓨터나 Release 빌드에서 갑자기 터지니까요.
term: 미정의 동작 | undefined behavior, UB | C++ 표준이 “무슨 일이 생길지 책임지지 않는다”고 정한 상황. 이상한 값, 매번 다른 결과, 프로그램 멈춤 모두 가능해요
tbl: 자주 만나는 미정의 동작 5가지
r: ① 값을 넣지 않은 변수 읽기
r: ② int가 담을 수 있는 범위를 넘기기 (오버플로)
r: ③ 반환형이 있는 함수에서 return 없이 끝나기
r: ④ 이미 사라진 객체나 널 포인터 건드리기
r: ⑤ 배열 범위 밖 칸 읽거나 쓰기
star: 중괄호 `{ }` 초기화는 값이 잘려 나가는 **축소 변환을 컴파일 오류로 막아 줘요**.
trap: `int x; std::cout << x;` > `int x {};` 로 만들고 읽기 > 값을 안 넣은 변수를 읽는 건 미정의 동작이에요
trap: `int n = 4.9;` 로 넣고 4.9가 들어갔다고 생각 > `double n { 4.9 };` 처럼 맞는 타입 사용 > int에는 소수점이 조용히 잘려 4가 들어가요
mem: `{ }` 는 울타리예요. 값이 줄어들어야 하면(4.9 → 4) 울타리를 못 넘어가요
key: 초기화는 `int x { 5 };`, 넣을 값이 없으면 `int x {};` (= 0)
key: `{ }` 는 축소 변환을 컴파일 오류로 잡아요
key: 값을 안 넣은 변수를 읽으면 미정의 동작

# p1-5 | 입출력, 이름 짓기, 표현식 | Ch 1.5, 1.7~1.10
sum: `std::cout <<` 로 화면에 내보내고 `std::cin >>` 로 키보드에서 받아요. 줄바꿈은 `'\n'` 을 써요. **표현식**은 값을 만들고, **문장**은 일을 시켜요.
ana: ➡️ 화살표 방향이 데이터가 흐르는 방향이에요. `cout << x` 는 x가 화면 쪽으로, `cin >> x` 는 키보드 입력이 x 쪽으로 흘러가요.
h: 입력받고 출력하기
code:
#include <iostream>
#include <string>

int main()
{
    std::string name {};
    int age {};
    std::cout << "이름과 나이: ";
    std::cin >> name >> age;                       // 공백을 기준으로 하나씩 읽어요
    std::cout << name << "님은 " << age << "살\n";
    return 0;
}
:end
out: 입력: 철수 20
이름과 나이: 철수 20
철수님은 20살
:end
p: `<<` 와 `>>` 를 여러 번 이어 쓸 수 있어요. `cin >> name >> age` 는 먼저 name을 읽고, 공백 다음 값을 age에 읽어요.
h: 줄바꿈은 '\n' 으로
tbl: 쓰는 법 | 차이
r: `'\n'` | 줄만 바꿔요. 빨라요 ✅
r: `std::endl` | 줄을 바꾸고, 출력 버퍼까지 비워요. 반복문 안에서 쓰면 눈에 띄게 느려져요
h: 이름 짓기 규칙
tbl: 반드시 지켜야 해요 | 지키면 좋아요
r: 영문자, 숫자, `_` 만 쓸 수 있어요 | 변수·함수는 소문자로 시작: `itemCount`
r: 숫자로 시작할 수 없어요 (`2count` ❌) | `_` 로 시작하는 이름은 피해요
r: `int`, `return` 같은 키워드는 못 써요 | 넓은 범위에서 쓰는 이름일수록 길고 분명하게
r: 대소문자를 구분해요 (`value` ≠ `Value`) | 
h: 표현식과 문장
p: **표현식**은 “계산하면 값이 하나 나오는 코드 조각”이에요. 표현식 뒤에 세미콜론을 붙이면 **문장**이 되고, 문장은 컴퓨터에게 일을 시켜요.
code:
int x { 2 + 3 };   // 2 + 3 은 표현식 → 값 5 가 나와요
x = x * 2;         // x * 2 도 표현식, 끝에 ; 를 붙여 문장이 됐어요 → x 는 10
:end
tbl: 말 | 뜻 | 예
r: 리터럴 | 코드에 직접 적은 고정값 | `5`, `3.14`, `'a'`, `"hi"`, `true`
r: 연산자 | 값으로 새 값을 만드는 기호 | `+`, `*`, `=`
r: 표현식 | 값 하나를 만드는 조각 | `2 + 3` → 5
r: 문장 | 표현식 + `;` | `x = 4;`
star: 줄바꿈은 기본으로 `'\n'` 을 써요. `std::endl` 은 버퍼까지 비워서 느려요.
trap: 반복문 안에서 `std::endl` 로 줄바꿈 > `'\n'` > 매번 버퍼를 비워서 느려져요
trap: 변수 이름을 `2count` 로 지음 > `count2` > 이름은 숫자로 시작할 수 없어요
mem: 표현식은 **값**을 만들고, 문장은 **일**을 시켜요
key: 출력은 `<<`, 입력은 `>>`, 줄바꿈은 `'\n'`
key: 이름은 영문자·숫자·`_`, 숫자로 시작 불가, 대소문자 구분
key: 표현식 + `;` = 문장

# p1-6 | 함수 만들기: 매개변수, 인자, 반환값 | Ch 2.1~2.4
sum: 함수를 만들 때 적는 변수가 **매개변수**, 부를 때 넣는 값이 **인자**예요. 인자는 **복사**돼서 들어가요. 반환형이 있는 함수는 모든 경우에 return 해야 해요.
ana: 🧾 매개변수는 주문서의 빈칸이고, 인자는 손님이 그 빈칸에 적어 낸 값이에요. 주방에는 주문서의 **복사본**이 들어가요. 주방에서 복사본에 낙서해도 손님 주문서는 그대로예요.
h: 함수의 생김새
code:
#include <iostream>

int add(int a, int b)   // int: 돌려줄 값의 타입 / add: 이름 / a, b: 매개변수
{
    return a + b;       // 값을 돌려주고 함수가 즉시 끝나요
}

int main()
{
    int sum { add(3, 4) };   // 3, 4 가 인자 → a=3, b=4 로 복사돼 들어가요
    std::cout << sum << '\n';
    return 0;
}
:end
out: 실행 결과
7
:end
tbl: 말 | 어디에 있나요 | 위 코드에서
r: 매개변수 (parameter) | 함수를 **만드는** 쪽 | `int a`, `int b`
r: 인자 (argument) | 함수를 **부르는** 쪽 | `3`, `4`
r: 반환값 | `return` 뒤의 값 | `a + b` → 7
h: 인자는 복사돼서 들어가요
p: 그래서 함수 안에서 매개변수를 바꿔도 부른 쪽의 원래 변수는 바뀌지 않아요. 이걸 **값에 의한 전달**이라고 해요.
code:
#include <iostream>

void addOne(int x)   // void: 돌려주는 값이 없음
{
    x = x + 1;       // 복사본 x 만 6 이 돼요
}

int main()
{
    int n { 5 };
    addOne(n);
    std::cout << n << '\n';   // 원본 n 은 그대로
    return 0;
}
:end
out: 실행 결과
5
:end
p: 원본을 바꾸고 싶다면 3회차에서 배우는 **참조(`int&`)** 를 써야 해요.
h: return 규칙
p: 반환형이 int처럼 정해진 함수는, 어떤 경우로 실행되든 반드시 return을 만나야 해요. 한 갈래라도 빠지면 그 경우에 무슨 값이 돌아올지 몰라 미정의 동작이 돼요.
vs: ❌ return 이 빠진 갈래 | ✅ 모든 갈래에 return
int sign(int x)
{
    if (x > 0)
        return 1;
    // x 가 0 이하면?
    // → return 없이 끝남 (UB)
}
--
int sign(int x)
{
    if (x > 0)
        return 1;
    return 0;
}
:end
tbl: 상황 | 결과
r: 반환형이 있는데 return 없이 끝나는 갈래가 있음 | ❌ 미정의 동작 (`-Wall` 이 경고해 줘요)
r: **main** 함수만 return을 생략 | ✅ 자동으로 `return 0;` 으로 처리돼요
r: 반환값을 쓰지 않고 `add(3, 4);` 만 호출 | ✅ 괜찮아요. 값이 버려질 뿐
r: void 함수의 반환값을 쓰려고 함 | ❌ 컴파일 오류
tip: 함수 하나는 일 하나만 하게 만들어요. 함수가 화면을 넘어갈 만큼 길어지면 대개 일을 두 개 이상 하고 있는 거예요.
star: return을 생략해도 되는 함수는 **main 하나뿐**이에요.
trap: 원본을 바꾸려고 `void addOne(int x)` 안에서 x를 바꿈 > `void addOne(int& x)` (3회차 참조) > 값으로 받으면 복사본만 바뀌어요
trap: if 갈래 하나에서 return을 빠뜨림 > 함수 끝에 기본 return 추가 > 그 경우로 실행되면 미정의 동작이에요
mem: **매**개변수 = **만**드는 쪽 빈칸, **인**자 = 실제로 **넣**는 값
key: 매개변수(만드는 쪽) ↔ 인자(부르는 쪽)
key: 인자는 복사돼 들어가서 원본이 안 바뀌어요
key: 반환형이 있으면 모든 갈래에 return (main만 예외)

# p1-7 | 선언과 정의, 그리고 ODR | Ch 2.7~2.12
sum: **선언**은 “이런 함수가 있어요”라는 한 줄 소개이고, **정의**는 실제로 일을 하는 몸통이에요. 선언은 여러 번 써도 되지만, **같은 함수의 몸통은 프로그램 전체에 하나만** 있어야 해요(ODR).
ana: 📇 선언은 명함, 정의는 실제 사람이에요. 명함은 여러 장 뿌려도 되지만, 같은 사람이 두 명이면 누구를 불러야 할지 몰라 곤란해요.
h: 먼저 상황부터
p: 컴파일러는 파일을 위에서 아래로 **한 번만** 읽어요. 그래서 아래쪽에 있는 함수를 위에서 부르면, 그 순간에는 아직 그 함수를 모르기 때문에 오류가 나요.
code:
#include <iostream>

int main()
{
    std::cout << add(3, 4) << '\n';   // ❌ 오류: add 를 아직 못 봤어요
    return 0;
}

int add(int a, int b)
{
    return a + b;
}
:end
out: 컴파일 오류
error: 'add' was not declared in this scope
:end
h: 해결: 위에 선언 한 줄 써 두기
p: 몸통 없이 함수의 모양만 적고 세미콜론으로 끝내면 **선언(전방 선언)** 이 돼요. 이 한 줄만 있으면 컴파일러는 “아, 이런 함수가 어딘가 있구나” 하고 넘어가요.
code:
#include <iostream>

int add(int a, int b);                // 선언: 이름과 모양만 (몸통 없이 ; 로 끝)

int main()
{
    std::cout << add(3, 4) << '\n';   // ✅ 이제 OK
    return 0;
}

int add(int a, int b)                 // 정의: 실제로 일을 하는 몸통
{
    return a + b;
}
:end
out: 실행 결과
7
:end
tbl:  | 선언 | 정의
r: 생김새 | `int add(int a, int b);` — 몸통 없이 `;` | `int add(int a, int b) { ... }` — 몸통 있음
r: 몇 번 써도 되나요 | 여러 번 OK | **같은 함수는 프로그램 전체에서 한 번만**
r: 빠뜨리면 | 컴파일 오류 (모르는 이름) | **링크 오류** (`undefined reference`)
h: ODR: 같은 함수의 몸통은 하나만
p: ODR(One Definition Rule)은 “함수를 하나만 만들 수 있다”는 뜻이 **아니에요**. add, sub, print처럼 다른 함수는 얼마든지 만들 수 있어요. 금지되는 건 **똑같은 함수의 몸통이 두 개** 있는 경우예요.
code:
// a.cpp
int add(int a, int b) { return a + b; }

// b.cpp
int add(int a, int b) { return a + b; }   // ❌ 같은 몸통이 또 있어요
:end
p: 이렇게 두 파일에 같은 몸통이 있으면, 링커가 조각을 이어 붙이다가 “add가 두 개인데 어느 걸 써야 하지?” 하고 링크 오류를 내요.
h: 그래서 파일은 이렇게 나눠요
p: 여러 파일이 같이 쓰는 함수는 **헤더(.h)에 선언**만 두고, **몸통은 .cpp 한 곳**에만 둬요. 헤더는 `#include` 하는 파일마다 복사되기 때문에, 헤더에 몸통을 두면 같은 몸통이 여러 개 생겨 버려요.
code:
// ── add.h ── (선언만)
#ifndef ADD_H        // 헤더 가드: 같은 헤더가 두 번 들어오는 걸 막아요
#define ADD_H
int add(int a, int b);
#endif

// ── add.cpp ── (몸통은 여기 한 곳)
#include "add.h"
int add(int a, int b) { return a + b; }

// ── main.cpp ── (선언을 가져와서 사용)
#include <iostream>
#include "add.h"
int main() { std::cout << add(3, 4) << '\n'; }
:end
p: 빌드는 `g++ main.cpp add.cpp -o app` 처럼 두 .cpp를 같이 넘겨야 해요. add.cpp를 빼먹으면 몸통이 없어서 링크 오류가 나요.
tip: 헤더 가드 세 줄 대신 헤더 맨 위에 `#pragma once` 한 줄을 써도 같은 효과가 있어요.
star: 선언만 있고 몸통이 없으면 **컴파일은 통과하고 링크에서 `undefined reference` 오류**가 나요.
star: 헤더에 함수 몸통을 쓰고 여러 .cpp에서 include하면 같은 몸통이 여러 개 생겨 **링크 오류**가 나요.
trap: 헤더(.h)에 함수 몸통까지 씀 > 헤더엔 선언만, 몸통은 .cpp 한 곳에 > include할 때마다 몸통이 복사돼 ODR 위반이 돼요
trap: 선언 끝에 세미콜론을 빠뜨림 `int add(int a, int b)` > `int add(int a, int b);` > 몸통이 이어질 거라고 생각해서 컴파일 오류가 나요
mem: 명함(선언)은 여러 장, 사람(정의)은 한 명
key: 선언 = 몸통 없이 `;`, 정의 = 몸통 있음
key: 같은 함수의 몸통은 프로그램 전체에 하나 (ODR)
key: 헤더엔 선언, .cpp엔 몸통

# p1-8 | 네임스페이스와 전처리기 | Ch 2.9~2.10
sum: 이름이 겹칠 때는 **네임스페이스**로 구분해요(`math::add`). `using namespace std;` 는 쓰지 않아요. 전처리기는 C++ 문법을 모르고 **글자를 바꿔치기**만 해요.
ana: 🏫 네임스페이스는 반 이름이에요. “1반 철수”, “2반 철수”라고 부르면 이름이 같아도 안 헷갈려요. `::` 가 “~반의”라는 뜻이에요.
h: 이름이 겹치면 어떻게 될까요?
p: 큰 프로그램에서는 여러 사람이 만든 코드에 같은 이름의 함수가 있을 수 있어요. 네임스페이스로 묶으면 이름이 같아도 따로 부를 수 있어요.
code:
#include <iostream>

namespace math    { int add(int a, int b) { return a + b; } }
namespace physics { int add(int a, int b) { return a + b + 100; } }

int main()
{
    std::cout << math::add(3, 4) << '\n';      // math 반의 add
    std::cout << physics::add(3, 4) << '\n';   // physics 반의 add
    return 0;
}
:end
out: 실행 결과
7
107
:end
p: 우리가 매번 쓰는 `std::cout` 도 같은 원리예요. 표준 라이브러리의 이름은 전부 `std` 라는 네임스페이스 안에 있어요.
h: using namespace std; 를 쓰지 않는 이유
p: `using namespace std;` 를 쓰면 std 안의 이름 수백 개가 한꺼번에 밖으로 나와요. 그러면 내가 만든 `count`, `data`, `distance` 같은 이름과 조용히 부딪힐 수 있어요.
tbl: 방법 | 괜찮을까요?
r: 파일 맨 위 `using namespace std;` | ❌ 이름 충돌 위험
r: 헤더 파일에 `using namespace std;` | ❌❌ 그 헤더를 include하는 **모든 파일**에 퍼져요
r: 함수 안에서 `using std::cout;` | ✅ 필요한 이름만, 좁은 범위에서
r: 그냥 `std::cout` 이라고 쓰기 | ✅ 가장 확실해요
h: 전처리기가 하는 일
p: 전처리기는 컴파일보다 먼저 돌아가는 “글자 바꿔치기 프로그램”이에요. C++ 문법을 이해하지 못해요.
tbl: 지시문 | 하는 일
r: `#include <파일>` | 그 파일 내용을 이 자리에 통째로 붙여 넣어요
r: `#define MAX 100` | 이후에 나오는 `MAX` 라는 글자를 `100` 으로 바꿔요
r: `#ifdef DEBUG` ~ `#endif` | 조건이 안 맞으면 그 사이 코드를 아예 지워요
li: `#define` 으로 만든 이름(매크로)은 정의한 곳부터 **그 파일 끝까지만** 유효해요. 다른 .cpp에는 영향이 없어요
li: 상수가 필요하면 매크로 대신 `constexpr` 변수를 써요 (2회차)
star: `using namespace std;` 는 쓰지 않아요. 특히 **헤더 파일에는 절대** 쓰지 않아요.
trap: 헤더에 `using namespace std;` > 필요한 곳에서 `std::` 를 붙이거나 함수 안에서 `using std::cout;` > 그 헤더를 쓰는 모든 파일에 이름 충돌이 퍼져요
trap: a.cpp의 `#define` 을 b.cpp에서 쓰려고 함 > 공통 헤더에 두거나 constexpr 상수 사용 > 매크로는 그 파일 안에서만 유효해요
mem: `::` = “~반의” (`math::add` = math반의 add)
key: 이름 충돌은 `네임스페이스::이름` 으로 구분
key: `using namespace std;` 는 쓰지 않기
key: 전처리기는 문법을 모르는 글자 바꿔치기

# p1-9 | 디버깅: 버그를 찾는 방법 | Ch 3.1~3.10
sum: 문법 오류는 컴파일러가 알려 주지만, **문법은 맞는데 결과가 틀린 오류**는 내가 찾아야 해요. 짐작하지 말고 **범위를 좁혀 가며** 찾아요.
ana: 🔦 정전된 집에서 고장 난 차단기를 찾는 것과 같아요. 아무거나 눌러 보지 말고, 절반씩 꺼 보면서 범위를 좁히면 금방 찾아요.
h: 오류의 두 종류
tbl:  | 구문 오류 (syntax error) | 의미 오류 (semantic error)
r: 뜻 | 문법이 틀림 | 문법은 맞는데 결과가 내 의도와 다름
r: 예 | `int x { 5 }` (세미콜론 빠짐) | 5번 돌리려 했는데 6번 도는 반복문
r: 누가 찾나요 | 컴파일러가 줄 번호까지 알려 줘요 | **내가** 찾아야 해요
code:
#include <iostream>

int main()
{
    for (int i { 0 }; i <= 5; ++i)   // 5번 출력하려고 했는데...
        std::cout << i << ' ';
    return 0;
}
:end
out: 실행 결과 — 6개가 나와요
0 1 2 3 4 5
:end
p: 컴파일러는 아무 말도 하지 않아요. 문법상으로는 아무 문제가 없으니까요. `<=` 를 `<` 로 바꿔야 5번이 돼요. 이렇게 하나 차이로 틀리는 걸 **off-by-one** 이라고 해요.
h: 버그를 찾는 다섯 단계
flow: 1 재현 > 매번 똑같은 방법으로 버그가 나게 만들어요 || 2 범위 좁히기 > 중간 지점의 값을 확인해서 앞쪽 문제인지 뒤쪽 문제인지 나눠요 || 3 원인 확인 > 그 지점의 값이 예상과 다른지 봐요 || 4 고치기 > 증상이 아니라 **원인**을 고쳐요 || 5 다시 확인 > 고쳐졌는지, 다른 곳이 망가지지 않았는지
warn: 결과가 1 크게 나온다고 `- 1` 을 붙여 숫자만 맞추면 안 돼요. 원인이 그대로 남아서 다른 곳에서 또 터져요.
h: 디버거 쓰는 법
p: 출력문(`std::cout`)을 여기저기 넣어 값을 찍어 볼 수도 있지만, 디버거를 쓰면 코드를 고치지 않고도 실행을 멈춰 놓고 변수 값을 볼 수 있어요.
tbl: 기능 | 하는 일
r: 중단점 (breakpoint) | 그 줄에 오면 실행을 멈춰요
r: Step **over** | 다음 줄로. 함수 호출은 통째로 실행하고 넘어가요
r: Step **into** | 다음 줄로. 함수 호출이면 그 함수 **안으로** 들어가요
r: Step **out** | 지금 함수를 끝까지 실행하고 **밖으로** 나와요
r: 변수 감시 (watch) | 변수 값을 실시간으로 보여 줘요
r: 호출 스택 (call stack) | 어떤 함수들을 거쳐 여기까지 왔는지 보여 줘요
tip: 디버거는 **Debug 빌드**에서 써야 해요. Release에서는 최적화 때문에 줄 순서가 뒤섞이고 변수가 “최적화되어 사라짐”으로 보여요.
h: 버그를 미리 막는 습관
li: 경고를 최대로 켜요: `-Wall -Wextra`. 비용 대비 효과가 가장 커요
li: 20줄쯤 쓸 때마다 컴파일하고 실행해 봐요. 200줄 쓰고 한꺼번에 고치면 어디가 문제인지 몰라요
li: 컴파일 오류가 여러 개 나면 **첫 번째 오류부터** 고쳐요. 오류 하나가 뒤에 오류 수십 개를 만들어요
star: 컴파일 오류가 많이 나오면 **첫 번째 오류부터** 고쳐요.
star: 문법은 맞는데 결과가 틀린 **의미 오류는 컴파일러가 잡아 주지 못해요**.
trap: 결과가 1 크게 나와서 `- 1` 을 붙임 > 왜 1 큰지 원인을 찾음 > 증상만 가리면 원인이 남아 다른 곳에서 또 터져요
trap: Release 빌드로 디버깅 > Debug 빌드로 디버깅 > 최적화 때문에 흐름이 뒤섞여요
mem: into = 안으로 쏙, over = 건너뛰기, out = 밖으로 탈출
key: 구문 오류는 컴파일러가, 의미 오류는 내가 찾아요
key: 첫 오류부터, 범위를 절반씩 좁혀서
key: Step into(안으로) / over(통째로) / out(밖으로)

# p1-10 | 정수: 크기, 오버플로, unsigned | Ch 4.1~4.5
sum: 정수는 기본으로 **int** 를 써요. 담을 수 있는 범위를 넘으면 int는 **미정의 동작**, unsigned는 **한 바퀴 돌아 엉뚱한 값**이 돼요. 정수끼리 나누면 소수점은 **버려져요**.
ana: 🚗 int는 속도계 끝을 넘으면 차가 고장 나는 것(미정의 동작)이고, unsigned는 주행 거리계처럼 999999 다음에 000000으로 돌아가는 것(한 바퀴)이에요.
h: 기본 타입 한눈에
tbl: 종류 | 타입 | 보통 크기
r: 정수 | `short`, `int`, `long`, `long long` | 2 / 4 / 4~8 / 8 바이트
r: 실수 | `float`, `double` | 4 / 8 바이트
r: 참·거짓 | `bool` | 1 바이트
r: 문자 | `char` | 1 바이트
r: 없음 | `void` | (함수가 아무것도 돌려주지 않을 때)
h: 크기는 정해져 있지 않아요
p: 지금 쓰는 컴퓨터에서 int는 거의 다 4바이트예요. 하지만 C++ 표준이 “int는 정확히 4바이트”라고 약속한 건 아니에요. 표준이 약속하는 건 **최소 크기**와 **크기 순서**뿐이에요.
tbl: 표준이 약속하는 것 | 약속하지 않는 것
r: 순서: char ≤ short ≤ int ≤ long ≤ long long | int가 정확히 몇 바이트인지
r: 최소 크기: int는 적어도 16비트 | 모든 컴퓨터에서 같은 크기인지
p: 그래서 크기가 궁금하면 `sizeof(int)`, 범위 끝이 궁금하면 `std::numeric_limits<int>::max()` 로 직접 물어봐요. 4바이트 int는 대략 −21억 ~ +21억까지 담아요.
h: int가 넘치면 — 미정의 동작
p: 21억을 넘는 값을 int에 담으려고 하면 **오버플로**가 나요. 이때 “음수로 한 바퀴 돈다”고 흔히 생각하지만, 표준은 이걸 **미정의 동작**으로 정해 두었어요. 그래서 이미 넘친 뒤에 검사하는 코드는 그 자체가 위험해요.
vs: ❌ 이미 넘친 뒤에 검사 | ✅ 넘치기 전에 검사
bool willOverflow(int x)
{
    // x + 1 이 넘치면 이미 UB
    return x + 1 < x;
}
--
#include <limits>
bool willOverflow(int x)
{
    return x == std::numeric_limits<int>::max();
}
:end
term: 오버플로 | overflow | 타입이 담을 수 있는 범위를 넘는 것. int에서는 미정의 동작
h: 정수 나눗셈은 소수점을 버려요
code:
#include <iostream>

int main()
{
    int a { 7 }, b { 2 };
    std::cout << a / b << '\n';                       // 정수끼리 → 3
    std::cout << static_cast<double>(a) / b << '\n';  // 한쪽을 double로 → 3.5
    return 0;
}
:end
out: 실행 결과
3
3.5
:end
p: `static_cast<double>(a)` 는 “a를 double로 바꿔서 써 줘”라는 뜻이에요(1-11에서 자세히). 둘 중 하나만 실수여도 실수 나눗셈이 돼요.
h: unsigned를 피하는 이유
p: unsigned는 음수가 없는 정수예요. 0에서 1을 빼면 −1이 아니라 **가장 큰 수로 한 바퀴** 돌아가요. 오류도 경고도 없이 조용히 틀린 값이 나와서 찾기 어려워요.
code:
#include <iostream>

int main()
{
    unsigned int x { 3 };
    std::cout << x - 5 << '\n';   // -2 가 아니라...
    return 0;
}
:end
out: 실행 결과 (unsigned int가 32비트인 환경)
4294967294
:end
tbl: 범위를 넘으면 | int (부호 있음) | unsigned (부호 없음)
r: 결과 | 미정의 동작 | 한 바퀴 돌아요 (정의된 동작)
r: 위험한 점 | 최적화 때문에 이상하게 깨져요 | 조용히 거대한 수가 돼요
star: `7 / 2` 는 **3** 이에요. 정수끼리 나누면 소수점을 버려요.
star: 표준은 int의 **정확한 크기를 보장하지 않아요**. 최소 크기와 크기 순서만 보장해요.
trap: `int sum, count;` 로 `sum / count` 평균 계산 > `static_cast<double>(sum) / count` > 정수끼리 나눠서 소수점이 사라져요
trap: `x + 1 < x` 로 오버플로 검사 > `x == std::numeric_limits<int>::max()` > 넘친 순간 이미 미정의 동작이에요
mem: int는 넘치면 **고장**(UB), unsigned는 넘치면 **한 바퀴**(wrap)
key: 정수는 int, 크기는 컴퓨터마다 다를 수 있어요
key: int 오버플로 = 미정의 동작, unsigned = 한 바퀴
key: `7 / 2 == 3`, 실수 나눗셈은 한쪽을 double로

# p1-11 | 실수, bool, char | Ch 4.7~4.12
sum: 실수는 **근삿값**이라서 `==` 로 비교하면 안 돼요. bool은 출력하면 **1/0** 으로 나와요. char는 사실 **작은 정수**라서 `'A'` 는 65예요.
ana: 📏 실수는 눈금이 정해진 자로 길이를 재는 것과 같아요. 0.1에 딱 맞는 눈금이 없어서 0.1000000001처럼 가장 가까운 눈금으로 재요.
h: 실수는 근삿값이에요
code:
#include <iostream>

int main()
{
    std::cout << (0.1 + 0.2 == 0.3) << '\n';   // 같을까요?
    return 0;
}
:end
out: 실행 결과
0
:end
p: 0이 나왔다는 건 “같지 않다(false)”는 뜻이에요. 컴퓨터는 0.1을 2진수로 정확히 나타낼 수 없어서, 0.1 + 0.2가 실제로는 0.30000000000000004 같은 값이 돼요. 그래서 실수는 `==` 대신 “차이가 아주 작은지”로 비교해요(2회차 6.7절).
tbl: 알아 둘 것 | 내용
r: 기본 실수 타입 | **double** (float은 메모리가 정말 중요할 때만)
r: 정밀도 | float은 약 7자리, double은 약 16자리
r: `3.2e5` | 3.2 × 10⁵ = 320000 (과학적 표기법)
h: bool: 참과 거짓
code:
#include <iostream>

int main()
{
    bool ok { true };
    std::cout << ok << '\n';                    // 그냥 출력하면 1
    std::cout << std::boolalpha << ok << '\n';  // boolalpha를 붙이면 true
    return 0;
}
:end
out: 실행 결과
1
true
:end
li: 조건(`if`)에 숫자를 넣으면 **0만 거짓**이고 나머지는 모두 참이에요
li: `if (isEven == true)` 대신 `if (isEven)`, 거짓은 `if (!isEven)` 으로 써요
warn: `if (x = 5)` 는 비교가 아니라 **대입**이에요. x에 5가 들어가고, 5는 0이 아니라서 조건이 항상 참이 돼요. 비교는 `==` 예요.
h: char는 작은 정수예요
p: char에는 글자가 들어가는 것처럼 보이지만, 실제로는 그 글자의 **번호(문자 코드)** 가 들어 있어요. `'A'` 는 65번이에요. 화면에 출력할 때만 글자로 보여 줘요.
code:
#include <iostream>

int main()
{
    char ch { 'A' };
    std::cout << ch << '\n';                           // A
    std::cout << static_cast<int>(ch) << '\n';         // 65  — 숫자로 보기
    std::cout << ch + 1 << '\n';                       // 66  — 계산하면 int가 돼요
    std::cout << static_cast<char>(ch + 1) << '\n';    // B   — 다시 char로 바꾸면 글자
    return 0;
}
:end
out: 실행 결과
A
65
66
B
:end
p: 세 번째 줄을 보세요. `ch + 1` 은 계산하는 순간 char가 int로 바뀌어서(승격) 66이라는 숫자가 나와요. 글자 B를 보고 싶으면 다시 char로 바꿔야 해요.
term: static_cast | static_cast<타입>(값) | 값을 원하는 타입으로 바꾸는 C++ 방식. C 스타일 `(int)x` 보다 어떤 변환인지 분명히 보여요
warn: `std::cin >> ch;` 는 공백을 건너뛰고 **딱 한 글자만** 읽어요. “abc”를 입력하면 a만 읽고 bc는 남아서 다음 입력으로 딸려 가요.
star: `0.1 + 0.2 == 0.3` 은 **false** 예요. 실수는 `==` 로 비교하지 않아요.
star: `'A' + 1` 은 **66** 이에요. 계산하면 char가 int로 바뀌어요.

trap: `if (x = 5)` > `if (x == 5)` > `=` 는 대입이라 조건이 항상 참이에요
